## Why

Today the CLI is profile-shaped, not workspace-shaped. `vspcli --install <name>`
installs a frozen extension list from `profiles/<name>/extensions.json` regardless
of what the workspace actually contains. UX (font + color theme + icon theme) is
fused into the profile name itself — every toolchain ships in `-crisp` and
`-retina` variants, so the catalog is 22 profile dirs (11 toolchains × 2 looks),
and switching the look means switching profiles.

Three concrete pain points fall out of that:

1. **A new project has no obvious starting point.** The user picks a profile by
   name (`rust-profile-crisp`) but nothing in the workspace is consulted. There's
   no path to "I just opened a Cargo.toml — give me the rust toolchain plus my
   preferred look."
2. **Common ground is missing.** Every workspace, regardless of toolchain, wants
   shell / yaml / markdown / json / toml editing extensions. Today each profile
   re-lists those by hand, which drifts.
3. **Look-vs-toolchain coupling forces double maintenance.** `cpp-clangd-crisp`
   and `cpp-clangd-retina` differ only in `_shared/editor-{crisp,retina}.jsonc`
   merge order. Eleven flavors × two looks compounds every change to either
   axis.

A fourth pain point is operational: there is no enforced rtk routing for shell
work driven from VS Code (interactive terminal or task runs), so an honest user
of the global RTK contract still ends up with bare `cargo`, `git`, and `rg`
invocations leaving the rtk telemetry blind. And rust API documentation
(rust-analyzer hover, `cargo doc` tasks, strict-docs gate) — which the team
considers a baseline — isn't pre-wired in any rust profile.

## What Changes

This change treats the workspace as the central object and pushes everything
else (toolchain layer, extensions, UX, rtk plumbing, rust docs, web/JS
templating) onto it as composable layers. Eight pieces, bundled because they
share the same workspace substrate, and **grounded in three existing reference
documents** that this change does not modify but does cite as the canonical
sources of truth:

- `docs/rust.md` — the four-layer Rust API documentation reference. The rust
  toolchain layer's settings + tasks derive directly from §2 and §11 of this
  doc; the agent docs policy block (§12) is appended to `AGENTS.md`,
  `CLAUDE.md`, `CODEX.md`, `GEMINI.md`.
- `docs/ts-js-node.md` — the TS/JS/Node templating analysis. The web/astro
  toolchain layer's framework auto-detection, the committed-vs-personal
  `.vscode/settings.json` split, the curated extension list, the
  Biome-or-ESLint+Prettier choice (mutually exclusive), and the
  `legacy: true` opt-in island all come from this doc. It also explicitly
  argues against using VS Code Profiles as the layering primitive — which
  is why this change collapses the profile catalog and pushes layers into
  `_shared/` and `.vscode/`.
- `docs/EXTENSION_COMPATIBILITY.md` — the user guide for
  `scripts/check-extension-compatibility.sh`. The layered install path
  gains a `--check-compat` flag that runs that script over the composed
  extension list before invoking `code`, and a `--check-compat=warn`
  variant that surfaces incompatibilities without blocking the install.

The eight pieces:

1. **Workspace toolchain detection** (new capability `detect-workspace-toolchain`):
   `vspcli --detect [PATH]` inspects signals at the workspace root
   (`Cargo.toml` → rust, `astro.config.{mjs,ts,js}` + `package.json` → astro,
   `pom.xml` → java-maven, `build.gradle*` → java-gradle, with Spring promoted
   when a `*Application.java` is found, `CMakeLists.txt` + `.clangd` → cpp-clangd,
   `CMakeLists.txt` alone → cpp-intellisense, `.github/workflows/*.yml` only →
   github-workflows). Polyglot repos stack all matching layers; `--toolchain
   <flavor>` forces a single layer; `--no-detect` falls back to user-supplied
   flavor only.

2. **Layered extensions** (modifies `install-profile-extensions`): every
   workspace gets a base layer (`shell/yaml/markdown/json/toml/.editorconfig`
   support extensions) plus the toolchain layer for the detected flavor. Layer
   sources move to `_shared/extensions/{base,<toolchain>}.json`; existing
   `profiles/<name>/extensions.json` is regenerated by composing them. **AI
   extensions reconciliation**: today's `rust-profile-crisp/extensions.json`,
   `cpp-clangd-crisp/extensions.json`, etc. include `github.copilot`,
   `anthropic.claude-code`, `openai.chatgpt`, `Continue.continue` directly,
   contradicting the README's documented "AI bundle: Copilot-only" policy
   for the `ai` flavor. The migration moves all AI-tagged extensions out of
   the toolchain layers into `_shared/extensions/ai.json` (Copilot subset)
   and `_shared/extensions/ai-plus.json` (Copilot + Claude + ChatGPT +
   Continue). Toolchain layers (`rust.json`, `cpp-clangd.json`, ...) carry
   only language tooling. Users who want AI in a non-AI workspace pass
   `--toolchain rust --toolchain ai` explicitly. README's AI policy badge
   is updated to match.

3. **Three install targets** (new `--target` flag on the install command):
   - `--target=workspace` (default for `--detect`) — write
     `.vscode/extensions.json` recommendations only; no install runs.
   - `--target=profile <name>` — today's behavior:
     `code --profile <name> --install-extension <id>`.
   - `--target=global` — machine-global per user:
     `code --install-extension <id>` with no `--profile` flag, lands in the
     user's default VS Code profile.

4. **UX moves to the workspace layer** (modifies `compose-profile-settings`):
   profiles become UX-agnostic. The UX key list is **derived mechanically**
   from `diff <(jq -S 'keys' _shared/editor-crisp.jsonc) <(jq -S 'keys'
   _shared/editor-retina.jsonc)` plus `diff <(jq _shared/editor-crisp.jsonc)
   <(jq _shared/editor-retina.jsonc)` — every key whose value differs between
   the two becomes a UX key. Spot-check at session start identified at least
   eight differing keys (`workbench.colorTheme`, `workbench.iconTheme`,
   `workbench.preferredDarkColorTheme`, `workbench.fontAliasing`,
   `workbench.tree.indent`, `terminal.integrated.fontSize`,
   `editor.fontSize`, `editor.lineHeight`) — the migration script
   re-derives the full set rather than hand-listing it.
   `_shared/ux/{crisp,retina}.jsonc` ship as the named UX presets;
   `_shared/editor-base.jsonc` ships with the ~80 non-UX keys that don't
   differ between crisp and retina (telemetry, update mode, autoFetch,
   format-on-save, GPU acceleration, etc.) and is layered into every
   profile's `_merged/<flavor>.json` so those settings don't regress to
   defaults post-migration. The CLI gains `--ux=crisp|retina` plus raw
   `--font`, `--font-size`, `--theme`, `--icon-theme` overrides. All four
   target `.vscode/settings.json` and merge key-by-key without trampling
   unrelated user-authored keys (modulo the comment-preservation non-goal
   above).

5. **Profile catalog collapse 22 → 11** (modifies `manage-profile-cli` and
   `export-profile-bundles`): drop the `-crisp`/`-retina` suffix; one toolchain
   profile per flavor. The 11 flavors: `rust`, `astro`, `java-maven`,
   `java-gradle`, `java-spring`, `cpp-clangd`, `cpp-intellisense`, `ai`,
   `ai-plus`, `github-workflows`, plus a tooling-only `general` profile that
   carries the ~80 non-UX shared keys (`telemetry.telemetryLevel`,
   `update.mode`, `extensions.autoUpdate`, `git.autofetch`,
   `files.trimTrailingWhitespace`, `terminal.integrated.gpuAcceleration`, ...)
   currently living in `_shared/editor-{crisp,retina}.jsonc`. (The
   placeholder `web` typescript flavor is **not** shipped this round and is
   not counted in the 11.) `vspcli --migrate-catalog` renames the
   directories, renames matching `_overrides/<flavor>-{crisp,retina}.jsonc`
   files, regenerates `_merged/<flavor>.json` and `exports/<flavor>.code-profile`
   atomically, and updates README references. The migration is `flock`-guarded
   against concurrent invocations and ships a `--doctor` mode that detects
   half-migrated state from a SIGKILL and reports remaining work.

6. **rtk enforcement via `.vscode/settings.json`** (additive, not a separate
   spec): the workspace defines a `terminal.integrated.profiles.osx.rtk-fish`
   profile (with `.linux` / bash equivalents) that sources
   `_shared/rtk/rtk-init.{fish,bash}` to install function-based wrappers
   (`rg`, `grep`, `find`, `git`, `cargo`, `npm`, etc., all routed through
   `rtk <cmd>` with a re-wrap guard). The fish/bash binary path is
   **detected at compose time** via `command -v fish` and `command -v
   bash` — NOT hardcoded to `/opt/homebrew/bin/fish` (which would break
   Linux contributors, Intel Macs, Codespaces, and devcontainers).
   `terminal.integrated.automationProfile.*` uses the same profile so task
   shells inherit the wrappers. Tasks in `.vscode/tasks.json` written by
   the CLI start every `command` with `rtk` literally, since VS Code
   provides no command-prepend hook. The change documents that this is
   convention + alias enforcement, not a hard block — VS Code has no
   native allow/deny for bare commands. **Workspace Trust fallback**:
   when Trust is denied (enterprise policy, headless CI, devcontainers
   that don't carry the workspace settings), the rtk init scripts emit
   a single stderr line on first interactive shell so users know
   wrappers didn't install; a `--no-rtk` flag on `vspcli --detect`
   suppresses the rtk wiring entirely for users who can't grant Trust.

7. **Rust API documentation stack** (folded into the rust toolchain layer): all
   four rustdoc surfaces enabled out-of-the-box for any rust-detected
   workspace — rustdoc comments (convention), rust-analyzer hover/signature
   docs (settings written to `.vscode/settings.json`), local `cargo doc` HTML
   (two tasks added to `.vscode/tasks.json`: `rust: doc` and `rust: doc strict`,
   the latter with `RUSTDOCFLAGS="-D warnings"`), and external/stdlib docs
   (handled by rust-analyzer, no extra config). The canonical reference is
   the existing `docs/rust.md` (14 sections + reality-check); a
   "Documentation Policy" block (extracted from §12 of that doc) is appended
   to `AGENTS.md`, `CLAUDE.md`, `CODEX.md`, `GEMINI.md`.

8. **Extensive BATS test coverage** as a non-negotiable phase. `scripts/tests/`
   gains a `bats/` subdirectory with one .bats file per surface
   (detection, layered install, workspace recs, UX overrides, catalog
   migration, CLI flags, rtk-init wrappers, rust docs settings + strict gate).
   `scripts/tests/run.sh` calls `bats scripts/tests/bats/*.bats`. CI gains a
   matrix job that installs `bats-core` + `bats-support` + `bats-assert` on
   ubuntu-latest (no macos runners).

**Cross-cutting constraints (apply to every script and test in this change):**

- All new executable scripts MUST be POSIX shell or `#!/usr/bin/env bash` —
  no Python, Node, or other runtimes. Matches the existing `scripts/`
  authoring contract.
- All new tests MUST be BATS (`*.bats`); no inline shell asserts in
  `run.sh`-style files for new coverage.
- All new shell MUST be shellcheck-clean (existing CI gate extended to new
  files).
- All new JSON/JSONC MUST pass the existing `validate-json.sh` / the
  `vscode-jsonc-validate` skill script.
- **JSONC comments are NOT preserved through merges** — the
  `scripts/lib/jsonc-merge.sh` helper uses `jq` (which destroys comments
  unconditionally), preserves the leading file-comment block as a string
  prefix on write-back, and writes a `.bak` sibling on first write so users
  can recover comments lost on a one-off basis. A node-based JSONC AST
  library is out of scope (would violate the shell-only constraint above).
  Documented as a non-goal so reviewers don't confuse it for an
  implementation gap.

**Deferred from this change to a follow-up** (called out so reviewers see
the boundary):

- Biome-vs-ESLint mutual exclusion handling for the web/astro toolchain
  layer — the design references `docs/ts-js-node.md`'s "pick one" rule but
  doesn't ship a `--tooling=biome|eslint` flag this round; the astro layer
  ships only the framework-detection extensions and a Biome default. The
  follow-up will add the flag, the conflict-resolution scenarios, and the
  legacy-island opt-in.
- A `web` typescript flavor (package.json without astro.config.\*) — the
  detection signal is reserved but no toolchain layer ships this round.

## Capabilities

### New Capabilities

- `detect-workspace-toolchain`: signal-driven detection of toolchain flavor(s)
  from workspace contents, with deterministic precedence, polyglot stacking,
  and explicit `--toolchain` / `--no-detect` overrides.

### Modified Capabilities

- `install-profile-extensions`: adds the layered base+toolchain composition
  (sourced from `_shared/extensions/{base,<toolchain>}.json`), the three
  install targets (`workspace`, `profile`, `global`), and a `--dry-run` mode
  that prints what would be installed without invoking `code`.
- `compose-profile-settings`: adds workspace-level UX overrides
  (`--ux=crisp|retina`, `--font`, `--font-size`, `--theme`, `--icon-theme`)
  with key-level JSONC merge into existing `.vscode/settings.json`; emits the
  rust-analyzer hover/signature settings when the rust toolchain is in scope.
- `manage-profile-cli`: adds `--detect`, `--target`, `--ux`, `--font`,
  `--font-size`, `--theme`, `--icon-theme`, `--migrate-catalog`,
  `--toolchain`, `--no-detect`, `--dry-run` flags; the CLI completion
  scripts (bash/zsh/fish) ship updated.
- `export-profile-bundles`: regenerates `exports/*.code-profile` after the
  catalog collapse; bundles emit only the toolchain-flavor profile name
  (`ai-profile.code-profile`), not the `-crisp`/`-retina` variants.

## Impact

- **Code**: new `_shared/extensions/{base,<toolchain>}.json`, new
  `_shared/ux/{crisp,retina}.jsonc`, new
  `_shared/rtk/rtk-init.{fish,bash}`, new `scripts/detect-toolchain.sh`,
  new `scripts/lib/jsonc-merge.sh` (key-level merge helper used by both
  the UX and rtk plumbing), modifications to
  `scripts/install-extensions.sh`, `scripts/compose-settings.sh`,
  `scripts/export-profiles.sh`, `scripts/import-profile.sh`,
  `scripts/vspcli`, plus the three completion scripts under
  `scripts/.vspcli-completion.{bash,zsh,fish}`. New BATS suite under
  `scripts/tests/bats/`. New reference doc at `docs/rust-documentation.md`.
  Profile catalog renames under `profiles/`. Regenerated `exports/`.
  Edits to `AGENTS.md`, `CLAUDE.md`, `CODEX.md`, `GEMINI.md`,
  `README.md`, `CHANGELOG.md`.
- **APIs**: `vspcli` gains the flags listed under "Modified Capabilities".
  All existing flags remain functional; `--install <name>` still installs
  the composed extension list for the named profile, just sourced from
  layers instead of a frozen file.
- **Dependencies**: existing (`jq`, `code` CLI, `bash 4+` available via
  Homebrew but scripts stay 3.2-compatible per repo convention). New: `bats-core`
  for the test suite (CI-installed; not a runtime dep). `shellcheck`
  already in CI.
- **Backwards compatibility**: legacy profile names
  (`<flavor>-crisp`, `<flavor>-retina`) resolve to `<flavor>` plus an
  implied `--ux=<look>` for one release with a deprecation warning
  (rate-limited per CI run, ack-able via `ARTAGON_VSCODE_DEPRECATION_ACK`);
  removed in the release after that. The deprecation shim lives in
  `vspcli` AND in `scripts/install-extensions.sh` /
  `scripts/compose-settings.sh` so users invoking the underlying
  scripts directly (per current README) also get the soft-landing.
  Legacy `exports/<flavor>-{crisp,retina}.code-profile` files become
  symlinks to `exports/<flavor>.code-profile` for the deprecation
  window so README and external bookmarks pointing at
  `raw.githubusercontent.com/.../<flavor>-crisp.code-profile` continue
  to resolve. Existing `profiles/<name>/extensions.json` files
  continue to be installable; the regenerated composed output is
  **set-equivalent (order-independent) after dedup**, NOT
  byte-equivalent — current per-profile files have asymmetric ordering
  (rust-profile lists themes first; cpp-clangd interleaves
  alphabetically) and `github-workflows-crisp/extensions.json` uses
  one-line-per-entry compact JSON while every other profile is
  multi-line. A single composer cannot reproduce all three
  formattings; the migration deliberately canonicalizes to one form.
- **Migration**: `vspcli --migrate-catalog` is a one-shot,
  idempotent-on-rerun command that renames profile dirs, regenerates
  `exports/`, and writes a `MIGRATED.md` note recording which legacy
  names were collapsed into which flavor.
- **Workspace Trust**: the rtk-fish terminal profile and the
  automationProfile only apply once the user grants Workspace Trust to
  the cloned repo. The README onboarding section documents this as a
  one-time click.
- **Risk**: medium. The catalog collapse touches every consumer of
  `vspcli` and every existing `exports/*.code-profile` filename. The
  layered-extensions composition risks producing a slightly different
  `extensions.json` byte-for-byte if a layer is sorted differently —
  the regression test for §2 below pins the composed output against the
  current canonical files until the collapse is complete.
