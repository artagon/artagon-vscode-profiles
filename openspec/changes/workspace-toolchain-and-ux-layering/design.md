## Context

Today the CLI is shaped around **profiles** as the unit of work, but the user's
mental model is shaped around **workspaces** ("I'm opening a Cargo.toml — give
me Rust tooling"). The repo's 22 profile directories collapse two orthogonal
axes into the catalog: toolchain (11 flavors) × look (crisp/retina). Common
"every workspace wants this" extensions (shell/yaml/markdown/json/toml) are
duplicated across the per-profile `extensions.json` files. Rust API
documentation enablement (rust-analyzer hover, `cargo doc` tasks, strict-docs
gate) — which the team treats as baseline — is not pre-wired in any rust
profile, so users replay the same `.vscode/settings.json` edits in every Rust
repo. And there is no enforced rtk routing for shell work invoked from VS
Code's terminal or task runs, leaving the rtk telemetry blind on a sizeable
share of invocations.

This change relocates the center of gravity from "named profile" to "detected
workspace + composable layers." The eight pieces in `proposal.md` share the
same workspace substrate and are bundled because splitting them would force
two migrations of `profiles/` and two regenerations of `exports/`.

## Goals / Non-Goals

**Goals:**

- The user can run `vspcli --detect` in any project root and have the right
  toolchain extensions + UX preset + rtk wiring + (for Rust) doc tasks land in
  `.vscode/`, without naming a profile by hand.
- Workspaces opened by anyone on the team get rtk-routed terminals and tasks
  by default once Workspace Trust is granted — no per-developer tweak.
- Rust API documentation (all four layers per `docs/rust-documentation.md`) is
  enabled for every detected Rust workspace with zero opt-in.
- The profile catalog is one toolchain × one workspace UX preset, not the
  Cartesian product.
- Every shell script introduced or modified by the change passes shellcheck
  clean and is exercised by a BATS test that pins its CLI contract (exit code
  + stdout/stderr + filesystem state) — no "smoke ran once" coverage.
- Legacy profile names continue to resolve for one release (with deprecation
  warning), so this change does not strand existing users mid-stream.

**Non-Goals:**

- Inventing a workspace settings *deep-merge*. VS Code's own behavior is
  key-level overlay (objects merge, primitives/arrays replace); the CLI
  matches that exactly. Anyone who wanted finer-grained merging should set
  the keys explicitly.
- Hard-blocking bare commands inside the workspace. VS Code provides no hook
  to refuse to run `cargo` (vs. `rtk cargo`). The rtk enforcement is
  convention + alias-driven and is documented as such; teams that need a
  hard block must reach for OS / org policy outside this repo.
- Adding a Python toolchain layer in this round. `pyproject.toml` /
  `requirements.txt` are reserved as detection signals for a future change;
  no extensions are wired up yet.
- Mirroring docs.rs offline, auto-launching the user's browser for `cargo
  doc`, or shipping anything that pretends to guarantee MCP semantic-context
  exposure of rustdoc. Treat MCP capabilities as runtime-discovered.
- Multi-root `.code-workspace` per-folder UX overrides. The CLI targets a
  single workspace root; multi-root is a future change. (VS Code's own
  multi-root rules drop window-scoped settings from per-folder
  `.vscode/settings.json` anyway, so the single-root path is strictly safer
  to ship first.)

## Decisions

### Decision 1: Layer sources live under `_shared/`, not `profiles/`

**Choice**: introduce `_shared/extensions/{base,<toolchain>}.json` and
`_shared/ux/{crisp,retina}.jsonc`. The existing
`profiles/<flavor>/extensions.json` files become **composed output**,
regenerated by `scripts/compose-settings.sh` (or a new
`scripts/compose-extensions.sh`), not hand-edited.

**Rationale**: this mirrors how `_shared/editor-{crisp,retina}.jsonc` already
provides settings layers and how `_overrides/` provides per-profile setting
overrides. The base+toolchain composition fits cleanly alongside that pattern.
Storing layers under `profiles/` would conflate "the source of truth" with
"the rendered result."

**Alternatives considered**:

- *One declarative `toolchains.yaml`*: a single file mapping detection signals
  → extension IDs. Rejected because it forces a JSON↔YAML format split (the
  rest of the repo is JSON/JSONC) and because per-flavor reviewability is
  better when each layer is its own file.
- *Keep layers per-profile*: ship base extensions in every
  `profiles/<flavor>/extensions.json` directly. Rejected because that's the
  duplication this change is meant to delete.

### Decision 2: Detection precedence is deterministic and explicit

**Choice**: document a fixed precedence list and stack all matching layers in
that order when polyglot. `--toolchain <flavor>` overrides; `--no-detect`
suppresses entirely.

Precedence (highest to lowest, when stacking is enabled — the order also
governs which layer's UX preset wins if both layers carry one):

1. `rust` (Cargo.toml present)
2. `cpp-clangd` (CMakeLists.txt + .clangd)
3. `cpp-intellisense` (CMakeLists.txt without .clangd)
4. `java-spring` (build.gradle* + a `*Application.java` with `@SpringBootApplication`)
5. `java-gradle` (build.gradle / build.gradle.kts, no Spring marker)
6. `java-maven` (pom.xml)
7. `astro` (package.json + astro.config.{mjs,ts,js})
8. `web` (package.json without astro.config — reserved for future TypeScript flavor)
9. `github-workflows` (.github/workflows/\*.yml only)
10. (reserved) `python` (pyproject.toml or requirements.txt)
11. `ai` / `ai-plus` — never auto-detected; opt-in via `--toolchain ai` only.

**Rationale**: a fixed list is testable in BATS with one fixture-repo per
combination. A scoring or "most files of type" heuristic would be
non-deterministic at the bin edges and harder to debug.

**Alternatives considered**:

- *Highest-priority single match*: pick rust over java-maven if both signals
  exist. Rejected because real polyglot repos (e.g., a Tauri app with a Rust
  core and a TypeScript shell) genuinely want both layers.
- *Interactive prompt on multi-match*: the CLI is used in CI and headless
  contexts where prompting fails. Stacking by default + `--toolchain` to
  pin is non-interactive-safe.

### Decision 3: Three install targets, one flag

**Choice**: add `--target=workspace|profile|global` to the install path:

- `workspace` (default for `--detect`): write `.vscode/extensions.json`
  recommendations only. No `code` invocation.
- `profile <name>`: today's behavior — `code --profile <name>
  --install-extension <id>`.
- `global`: `code --install-extension <id>` with no `--profile` flag, lands
  in the user's default VS Code profile.

The default for the existing `--install <name>` command stays
`--target=profile <name>` for backwards compatibility.

**Rationale**: each target has a real use case — workspace recommendations
for a shared repo, profile install for a curated VS Code profile, machine-
global install for "I just want this everywhere I open VS Code on this
laptop." Conflating them under one mode would silently install or fail to
install based on context.

**Alternatives considered**:

- *Drop the global target* and tell users to run `code --install-extension`
  themselves. Rejected — users have explicitly asked for it ("right now all
  extensions installed globally, I want to keep that option also") and it's
  a one-line dispatch difference.
- *Auto-pick target based on flags*: e.g., `--detect` → workspace, `--install
  <name>` → profile. Same end state, but explicit `--target` reads better in
  scripts and makes mutual-exclusion testing trivial.

### Decision 4: UX is a workspace overlay, not a profile axis

**Choice**: collapse the catalog from 22 → 11. Profiles carry only
toolchain-related settings (rust-analyzer config, java compiler config, etc.).
UX (font, color theme, icon theme) ships as `_shared/ux/{crisp,retina}.jsonc`
and is applied by the CLI at the workspace level via `--ux=crisp|retina`,
optionally layered with raw `--font` / `--font-size` / `--theme` /
`--icon-theme` overrides.

**Rationale**: VS Code already separates resource-scoped from
window-scoped settings, and the look is window-scoped. Putting it in the
workspace `.vscode/settings.json` matches VS Code's own scope model and
removes the catalog × 2 explosion.

**Alternatives considered**:

- *Keep 22 profiles, add a UX overlay anyway*: leaves the duplication in
  place. Rejected.
- *Drop crisp/retina entirely; let users set fonts by hand*: rejected —
  the named presets are how the team agrees on a look.
- *Keep 22 as aliases that resolve to the same toolchain + implied UX*: kept
  as the **migration shim** (one release with deprecation warning) but not
  the long-term shape.

### Decision 5: Migration via `vspcli --migrate-catalog`

**Choice**: ship a one-shot, idempotent-on-rerun migration command that
renames `profiles/<flavor>-{crisp,retina}/` to `profiles/<flavor>/`,
regenerates `exports/*.code-profile`, writes a `MIGRATED.md` note recording
which legacy names were collapsed, and updates README references in the
same pass. Legacy names continue to resolve for one release with a
deprecation warning written to stderr on every invocation; removed in the
release after.

**Rationale**: a script is more reviewable than a hand-merge PR because it
runs identically on developer machines and CI. The deprecation window
absorbs CI scripts and documentation that already pin profile names — they
work for one release without changes.

**Alternatives considered**:

- *Hard cut at the boundary release*: rejected — strands consumers
  mid-stream.
- *Symlink-based aliasing forever*: rejected — silent layout that doesn't
  age well; eventually someone removes the symlinks and is mystified.

### Decision 6: rtk enforcement is profile-driven aliases plus literal `rtk` in tasks

**Choice**: workspace `.vscode/settings.json` defines a custom
`terminal.integrated.profiles.osx.rtk-fish` (and `.linux` / a bash variant)
that sources `_shared/rtk/rtk-init.fish` (or `.bash`) via fish's
`--init-command` flag (or bash's `--rcfile`). The init script installs
function-based wrappers (`rg`, `grep`, `find`, plus build/test commands like
`git`, `cargo`, `npm`, `mvn`, `gradle`) that route through `rtk <cmd>`. A
re-wrap guard via the `ARTAGON_RTK_WRAPPED` env marker prevents infinite
recursion when `rtk` itself spawns child shells. `terminal.integrated
.automationProfile.osx` reuses the same profile so task shells inherit the
wrappers. `.vscode/tasks.json` entries written by the CLI start their
`command` field with `rtk` literally, because VS Code provides no
command-prepend hook (the automationProfile only chooses *which* shell, not
*what to prefix*).

**Rationale**: this is the only mechanism VS Code actually offers for
workspace-level shell enforcement. Documenting it as convention + alias is
honest; pretending the CLI hard-blocks bare commands would be a lie.

**Alternatives considered**:

- *Wrap the shell binary* (custom `fish` script that re-execs through rtk):
  rejected — fragile, breaks `command -v fish` and other tooling assumptions.
- *Patch every task author's `command` field automatically when writing
  tasks.json*: kept as part of the design (the CLI does write `rtk <cmd>`
  literally in tasks it generates). For tasks the user writes by hand, the
  init-script aliases catch direct invocations under fish-as-automation;
  scripts spawned from those tasks (e.g., a `bash build.sh`) escape the
  alias, which is documented.
- *Ship a `.envrc` or `direnv` config*: rejected — adds a third tool to the
  bootstrap path.

**Documented gotchas (incorporated into `docs/` as part of the change):**

1. `automationProfile` does NOT prepend `rtk`. It only chooses the shell.
2. `"type": "process"` tasks bypass the shell entirely — no aliases, no rtk.
3. Aliases don't propagate into subshells launched from a script.
4. `VAR=val cmd` task commands are bash-only; on fish use
   `rtk env VAR=val cmd ...` or wrap in `fish -c "set -lx VAR val; rtk cmd"`.
5. **Workspace Trust gates the rtk profile.** Until granted, the profile is
   silently ignored and the user gets a default shell with no wrappers. The
   README onboarding section documents this as a one-time click.
6. `unwantedRecommendations` in `.vscode/extensions.json` is *not*
   enforcement — it suppresses prompts only.
7. `security.workspace.trust.enabled` is application-scoped; a workspace
   cannot disarm Trust.
8. JSONC duplicate keys are silent — last-wins. The CLI's JSONC merge dedups
   before writing.

### Decision 7: Rust documentation stack is rust-toolchain-default, not opt-in

**Choice**: when `Cargo.toml` is detected, the rust toolchain layer applies
all four documentation layers automatically:

(a) rustdoc comments — convention only (documented in
`docs/rust-documentation.md`).
(b) rust-analyzer hover/signature docs — written to `.vscode/settings.json`:

```jsonc
{
  "rust-analyzer.hover.actions.enable": true,
  "rust-analyzer.hover.documentation.enable": true,
  "rust-analyzer.hover.links.enable": true,
  "rust-analyzer.signatureInfo.documentation.enable": true,
  "editor.hover.enabled": true,
  "editor.hover.delay": 300,
  "editor.parameterHints.enabled": true
}
```

(c) Local `cargo doc` HTML — two tasks added to `.vscode/tasks.json`:

```jsonc
{
  "label": "rust: doc",
  "type": "shell",
  "command": "rtk cargo doc --workspace --all-features --no-deps",
  "problemMatcher": "$rustc"
},
{
  "label": "rust: doc strict",
  "type": "shell",
  "command": "rtk env RUSTDOCFLAGS='-D warnings' cargo doc --workspace --all-features --no-deps",
  "problemMatcher": "$rustc"
}
```

Note: `rtk env` is used for the env-prefixed form so it works under both
fish and bash automation profiles. Plain `RUSTDOCFLAGS='...' rtk cargo
...` is bash-only.

(d) External crate / stdlib docs — handled by rust-analyzer hover; no
additional config required. Documented as such.

**Rationale**: every Rust workspace the team owns wants these. Asking each
user to opt-in re-introduces the per-developer drift this change is meant
to remove.

**Alternatives considered**:

- *Make the docs stack opt-in via `--rust-docs`*: rejected — opt-in defaults
  guarantee the bar drifts down over time.
- *Ship docs settings in `_shared/rust-docs.jsonc` separate from the
  toolchain layer*: rejected — it's a feature *of* the rust toolchain, not a
  parallel concern.

### Decision 8: BATS is the only test surface for new coverage

**Choice**: every new test goes under `scripts/tests/bats/` as a `*.bats`
file. Existing inline shell asserts in `scripts/tests/run.sh` are not
extended. The run.sh entry point is updated to invoke `bats
scripts/tests/bats/*.bats`.

**Rationale**: matches the existing investment in
`agents/skills/vscode-config/scripts/tests/*.bats` and gives us per-test
isolation (`$BATS_TEST_TMPDIR`), structured TAP output, and per-file tags
(e.g., `# bats file_tags=:no-parallel` for tests with shared env state).

**Alternatives considered**:

- *Wait for `migrate-tests-to-bats` (PR #3) to merge first, then layer this
  change on top*: that's strictly safer but couples this change to PR #3's
  timeline. The compromise (also followed by `profile-graceful-defaults`):
  write the new tests as BATS regardless; if the run.sh-to-BATS migration
  hasn't merged, the new BATS files run alongside the legacy run.sh inline
  asserts via a new `scripts/tests/run-bats.sh` entry point.

### Decision 9: All new scripts are shell; all new tests are BATS

**Choice**: enforce by review and by a CI gate (`shellcheck` over
`scripts/**` plus a check that every file under `scripts/tests/bats/` is a
`*.bats` file).

**Rationale**: matches the user's explicit constraint and the existing
`scripts/` authoring contract. No Python, Node, or other runtime
dependencies enter the bootstrap path.

## Reference: Rust API Documentation in VS Code

The canonical reference is the **existing `docs/rust.md`** (14 sections plus
the reality-check / adversarial review block). This change does not modify
that file; it derives concrete CLI behavior from it:

- §2 of `docs/rust.md` defines the rust-analyzer hover/signature settings
  the rust toolchain layer writes to `.vscode/settings.json` (verbatim,
  exactly the seven keys in §2's JSON block).
- §11 of `docs/rust.md` defines the two `cargo doc` tasks the rust
  toolchain layer writes to `.vscode/tasks.json` — the CLI-generated form
  prepends `rtk` (and uses `rtk env RUSTDOCFLAGS=...` for the strict
  variant) per Decision 6 above; the bare form in §11 is general-audience
  documentation.
- §12 of `docs/rust.md` defines the "Documentation Policy" block that gets
  appended to `AGENTS.md`, `CLAUDE.md`, `CODEX.md`, `GEMINI.md` during
  apply.
- The "Reality Check / Adversarial Review" block at the end of
  `docs/rust.md` enumerates the non-goals already captured in this
  design's "Goals / Non-Goals" section (no Smart Context MCP guarantee, no
  macro-doc magic, no docs.rs offline mirror, no auto-browser launch).

The CLI never *modifies* `docs/rust.md`. If the doc evolves, the rust
toolchain layer's settings/tasks regenerate from it on the next compose
run; pinning the layer's output against a snapshot of `docs/rust.md` is
how the BATS suite (Phase G) prevents silent drift.

### Decision 10: Web/Astro/TS toolchain layer follows `docs/ts-js-node.md`

**Choice**: the web, astro, and (reserved) typescript toolchain layers
import their architectural choices from `docs/ts-js-node.md` rather than
inventing parallel rules. Specifically:

- **Framework auto-detection** in `vspcli --detect`: the astro signal is
  `package.json` + `astro.config.{mjs,ts,js}`; the broader
  package.json-only path is reserved for future flavors and probes for
  `vue`, `svelte`, `next`, `solid`, `react` keys per the antfu pattern
  documented in `docs/ts-js-node.md` ("Framework layer: auto-detection
  beats explicit configuration"). The change adds the astro signal now;
  vue/svelte/react/next/solid land in a follow-up change once their
  toolchain layers exist.
- **Tooling layer mutual exclusion is DEFERRED to a follow-up change.**
  This round ships the astro toolchain layer with a Biome default (no
  `--tooling=biome|eslint` flag, no ESLint variant). The Biome/ESLint
  conflict-resolution logic (what to do when both `biome.json` and
  `eslint.config.ts` exist; what `--tooling=biome` does when only ESLint
  is present; legacy `.eslintrc.*` opt-in island) lives in a separate
  proposal once the astro layer is exercised by real users. Underspeccing
  it here was flagged in adversarial review as shipping a flag without a
  concrete spec scenario.
- **Committed `.vscode/settings.json` stays minimal** per the doc's "Base
  layer" section. The CLI writes only project-correctness keys
  (`editor.formatOnSave`, `editor.defaultFormatter` per language,
  `editor.codeActionsOnSave` for the chosen tooling, `eslint.validate` if
  ESLint, `typescript.tsdk: "node_modules/typescript/lib"`). Personal
  preferences (font, color theme, icon theme) stay in the UX layer
  (`_shared/ux/{crisp,retina}.jsonc`) — never in the toolchain layer.
- **Curated extension list** for the astro base comes from
  `docs/ts-js-node.md`'s "Curated extension list" table — only the
  always-on entries this round (`editorconfig.editorconfig`,
  `biomejs.biome`, `astro-build.astro-vscode`, `yoavbls.pretty-ts-errors`,
  `vitest.explorer`). `bradlc.vscode-tailwindcss` is gated on a tailwind
  config signal (deferred to the same follow-up that handles tooling
  mutex). ESLint/Prettier extensions ship in the deferred follow-up.
- **Legacy island deferred** to the same follow-up: `--legacy` flag,
  `.eslintrc.*` detection, the "five settings that make legacy survivable"
  set, and `unwantedRecommendations` blocking Biome — none of this ships
  this round. The astro layer does NOT carry `eslint.useFlatConfig`,
  `NODE_OPTIONS=--openssl-legacy-provider`, or any
  `unwantedRecommendations` entries.

**Rationale**: `docs/ts-js-node.md` did three rounds of adversarial review
on this surface and the conclusions are stable. Re-deriving the rules in
the OpenSpec change would invite drift; citing the doc as authoritative
keeps the two artifacts in sync.

**Alternatives considered**:

- *Re-derive in design.md from first principles*: would duplicate ~25KB of
  analysis already committed. Rejected.
- *Skip the web/astro layer this round*: rejected — astro is one of the
  named toolchains the user enumerated in scope, and the layer is small
  once `docs/ts-js-node.md` is the source.

### Decision 11: Extension compatibility check is opt-in pre-install with `warn` default

**Choice**: the layered install path gains a `--check-compat=block|warn|off`
flag that runs `scripts/check-extension-compatibility.sh --json` over the
composed extension list before invoking `code`. Three modes:

- `--check-compat=block`: incompatible extensions block the install with
  exit code 2 and the failing IDs on stderr. Opt-in only — never the
  default. Suited for CI gates that want a hard fail.
- `--check-compat=warn` (DEFAULT for all three install targets): print
  failing IDs to stderr; the install (or recommendation write) proceeds.
- `--check-compat=off`: skip the compat check entirely.

**Rationale**: the original draft inverted the defaults (block on
workspace, off on profile/global). Adversarial review flagged this as
upside-down: workspace recommendations are user-decline-able per-extension
in VS Code's UI; blocking the entire write because one ID has an
`engines.vscode` mismatch is more aggressive than any install path.
Conversely, `--target=global` directly invokes
`code --install-extension <id>` where the install would naturally fail on
real incompat — but defaulting to `off` there means users miss the early
warning. `warn` everywhere surfaces the issue without taking opinionated
action; teams that want a CI gate flip explicit `--check-compat=block`.

**Alternatives considered**:

- *Block by default for `workspace`*: rejected — recommendations should
  not over-gate.
- *Off by default everywhere*: rejected — silent skipping defeats the
  point of having the checker integrated.

### Decision 12: JSONC comment preservation is an explicit non-goal

**Choice**: `scripts/lib/jsonc-merge.sh` strips JSONC comments via
`agents/skills/vscode-config/scripts/jsonc-strip.awk` before passing the
input to `jq`, then writes back canonical JSON with the original file's
**leading comment block** restored as a string prefix. Comments interior
to the file (between keys) are lost. The CLI writes a `.bak` sibling on
first write to a previously-comment-bearing file so users can recover
on a one-off basis.

**Rationale**: adversarial review flagged the original "preserve comments
where possible" claim as impossible with the proposed jq-based pipeline.
The skill's tooling is a one-way stripper; there is no JSONC-aware
emitter in the repo. Building one would require a Node JSONC AST library
(violates the shell-only constraint) or a hand-rolled awk parser (high
maintenance). Honest non-goal beats a broken promise.

**Alternatives considered**:

- *Embed `eemeli/jsonc-parser` via a Node helper*: rejected — every other
  tool in `scripts/` is shell.
- *Hand-roll a JSONC AST in awk*: rejected — too much surface for too
  little gain. Most workspace `.vscode/settings.json` files have a
  leading comment block describing the workspace and no interior
  comments; the chosen behavior covers ~95% of real cases.
- *Refuse to merge into a file with interior comments*: rejected — too
  aggressive; users would need to delete comments to use the CLI.

### Decision 13: Terminal-profile shell paths are detected, not hardcoded

**Choice**: at compose time, `scripts/compose-settings.sh` resolves
`fish` and `bash` via `command -v` and emits the resolved absolute path
into `terminal.integrated.profiles.osx[*].path` and `.linux[*].path`.
When the binary is not on PATH, the profile entry is omitted (not
written with a stub path that would silently fail) and a stderr notice
explains the omission. `${workspaceFolder}` is used in `args` for the
`--init-command` source path; if VS Code does not substitute the
variable in that context (Open Question 1 below — must be validated
before merge), the migration script falls back to writing the absolute
path resolved at compose time.

**Rationale**: hardcoding `/opt/homebrew/bin/fish` (the original
draft's value) breaks every Linux contributor, Intel Mac, Codespace,
and devcontainer. Adversarial review flagged this independently in
both the design-gotchas and migration-risk lenses. Detection at
compose time is the only portable answer.

**Alternatives considered**:

- *Use `"path": "fish"` (PATH-resolved at runtime)*: VS Code documents
  that profile paths must be absolute on macOS for the icon-association
  + dock behavior; some flows reject relative paths. Tested form is
  absolute paths.
- *Ship a per-OS profile bundle*: kept — `terminal.integrated.profiles
  .osx` and `.linux` are populated with their detected paths
  independently.

### Decision 14: Workspace Trust fallback when rtk wiring can't apply

**Choice**: when Workspace Trust is denied (enterprise policy with
`security.workspace.trust.enabled` policy-locked, headless CI, or a
devcontainer that didn't receive the workspace settings), the rtk
profile is silently dropped by VS Code (Restricted Mode behavior
documented in the in-repo skill references). The change adds two
fallbacks:

1. The fish init script, when sourced manually, prints a single
   stderr line on first interactive shell: `"rtk wrappers active —
   workspace trust granted"` (success) or — when sourced but rtk is
   absent on PATH — the existing
   `"rtk not on PATH; aliases not installed"` line. Users who never
   see the success line know they're in Restricted Mode.
2. A new `--no-rtk` flag on `vspcli --detect` suppresses the rtk
   wiring entirely (no terminal profile, no `_shared/rtk/` files
   referenced from `.vscode/settings.json`). Intended for users on
   trust-locked enterprise machines, CI runners, and devcontainers
   that opt out of the wrapping.

**Rationale**: the original draft treated Workspace Trust as a
one-time click and had no story for users who can't grant it. That
silently breaks rtk for an entire class of contributors. The
fallback provides both a diagnostic ("did the wrappers install?")
and an opt-out (`--no-rtk`).

**Alternatives considered**:

- *Document Trust as a hard prerequisite*: rejected — disenfranchises
  enterprise users.
- *Auto-detect Restricted Mode and skip rtk wiring*: there's no API to
  detect it from a shell; would require reading VS Code's storage,
  which this change can't reliably do.

### Decision 15: AI extensions reconcile to `_shared/extensions/{ai,ai-plus}.json` only

**Choice**: today's per-toolchain `extensions.json` files in
`profiles/<flavor>-{crisp,retina}/` include `github.copilot`,
`github.copilot-chat`, `anthropic.claude-code`, `openai.chatgpt`, and
`Continue.continue` directly (verified in `rust-profile-crisp`,
`cpp-clangd-crisp`). README.md documents `ai-profile` as a
"Copilot-only by policy" bundle, contradicting the per-toolchain
content. The migration removes all AI-tagged extensions from the
toolchain layers (`_shared/extensions/rust.json` etc.) and consolidates
them into:

- `_shared/extensions/ai.json` — Copilot + Copilot Chat only.
- `_shared/extensions/ai-plus.json` — the AI bundle plus Claude,
  ChatGPT, Continue, Cody, Tabnine, Codeium.

Users who want AI in a non-AI workspace pass `--toolchain rust
--toolchain ai` (or `ai-plus`). Detection never auto-emits ai/ai-plus
(Decision 2 already excludes them from the precedence list). README's
"AI Copilot Only" badge is updated to match the new factoring.

**Rationale**: today's extension files have drifted from the documented
policy. The migration is a natural moment to enforce it. Layering
makes the policy reviewable (`_shared/extensions/ai.json` is the
authoritative AI list; if it's wrong, one PR fixes it everywhere).

**Alternatives considered**:

- *Add AI to `_shared/extensions/base.json` (every workspace)*:
  rejected — many users explicitly don't want AI.
- *Keep AI in toolchain layers + suppress in `ai-profile`*: rejected —
  doubles maintenance and keeps the README/code drift latent.

### Decision 16: `_shared/editor-base.jsonc` carries the ~80 non-UX shared keys

**Choice**: `_shared/editor-{crisp,retina}.jsonc` are decomposed
mechanically into:

- `_shared/editor-base.jsonc` — every key whose value is identical
  between crisp and retina (~80 keys: `update.mode`,
  `extensions.autoUpdate`, `extensions.ignoreRecommendations`,
  `terminal.integrated.gpuAcceleration`,
  `terminal.integrated.minimumContrastRatio`,
  `editor.guides.bracketPairs`, `files.trimTrailingWhitespace`,
  `git.autofetch`, `git.confirmSync`,
  `security.workspace.trust.untrustedFiles`, `telemetry.telemetryLevel`,
  ...). Always merged into every `_merged/<flavor>.json` post-migration.
- `_shared/ux/{crisp,retina}.jsonc` — every key whose value differs
  between crisp and retina. Applied at the workspace layer only.

The decomposition is performed by a one-shot script during the
migration; the script also asserts the key sets are disjoint (no key
appears in both files) and that their union equals the original
`_shared/editor-{crisp,retina}.jsonc` keys.

**Rationale**: original draft would have left these ~80 keys orphaned —
either silently dropped (so format-on-save, GPU acceleration, telemetry
opt-out etc. regress to defaults) or duplicated 11× (defeating the
"common ground is missing" rationale). A `_shared/editor-base.jsonc`
captures the cross-flavor invariant.

**Alternatives considered**:

- *Move every shared key into `_shared/extensions/base.json` as
  settings*: extensions.json doesn't carry settings — settings live
  in JSONC files only.
- *Embed the shared keys in each toolchain layer's settings file*:
  rejected — duplication.

### Decision 17: UX key list is derived mechanically, not hand-listed

**Choice**: the migration script computes the UX key list as `keys(
_shared/editor-crisp.jsonc) ∩ keys(_shared/editor-retina.jsonc) where
the value differs`. It does NOT hand-list keys. After the script runs,
both `_shared/ux/crisp.jsonc` and `_shared/ux/retina.jsonc` contain the
exact same set of keys (with different values). A CI gate asserts:

- `diff <(jq -S 'keys' _shared/ux/crisp.jsonc) <(jq -S 'keys'
  _shared/ux/retina.jsonc)` is empty (key sets identical).
- Every key in either file has a value-different counterpart in the
  legacy `_shared/editor-{crisp,retina}.jsonc` snapshot at migration
  time.
- `keys(_shared/ux/<preset>.jsonc) ∩ keys(_shared/editor-base.jsonc)`
  is empty (UX and base don't overlap).

**Rationale**: original draft's hand-listed UX keys missed at least
four real ones (`workbench.preferredDarkColorTheme`,
`workbench.fontAliasing`, `workbench.tree.indent`,
`terminal.integrated.fontSize`). Mechanical derivation prevents this
class of bug.

### Decision 18: Legacy bundle filenames become symlinks during deprecation

**Choice**: `vspcli --migrate-catalog` does NOT delete
`exports/<flavor>-{crisp,retina}.code-profile`. Instead, it replaces
each legacy bundle file with a symlink to the corresponding new
`exports/<flavor>.code-profile`. Symlinks remain through the deprecation
window. The release after that, `vspcli --migrate-catalog --finalize`
removes the symlinks (legacy file requests now 404).

**Rationale**: README.md has 14 hard-coded
`raw.githubusercontent.com/.../<flavor>-{crisp,retina}.code-profile`
URLs. External bookmarks, in-flight PR descriptions, Slack threads, and
team docs all hold those URLs. Hard-deleting them at migration time is
asymmetric with the legacy-name deprecation (legacy *names* get a soft
landing; legacy *URLs* would get a hard 404). Symlinks are the
filesystem-level equivalent of the deprecation shim.

**Trade-off**: GitHub serves symlinks as the file they target, so the
URL still resolves. Local clones see a symlink; if a user has scripted
around byte-content of the legacy bundles, they get the new bundle's
bytes — which is correct (the new bundle contains the same flavor's
extensions + a distinct UX preset, but UX is now applied at workspace
layer not in the bundle). Document this in CHANGELOG.

### Decision 19: Migration is `flock`-guarded with `--doctor` recovery

**Choice**: `scripts/migrate-catalog.sh` opens `flock 9 <repo>/.cache/
migrate-catalog.lock` at startup; concurrent invocations exit with code
6 and a "migration already running" message. Atomicity is achieved by
writing the new layout to a sibling tree (`profiles.new/`,
`exports.new/`, `_overrides.new/`, `_merged.new/`), atomically renaming
each tree into place via POSIX `rename(2)` (atomic on a single
filesystem), and removing the `.old` siblings on success. SIGKILL
between two atomic renames leaves a partially-renamed state that
`vspcli --migrate-catalog --doctor` detects and continues from.

**Rationale**: original draft's "remove failed file; restore from
backup" pseudocode wasn't actually atomic and didn't survive SIGKILL
without a re-run. POSIX `rename(2)` provides the only filesystem-level
transaction primitive available to shell. `flock` prevents the
concurrent-invocation footgun (CI + local developer racing on the same
checkout).

### Decision 20: Deprecation warnings are rate-limited and ack-able

**Choice**: legacy-name resolution prints the deprecation warning to
stderr **once per process tree** (not once per invocation). The first
invocation in a CI run prints it; subsequent invocations within the same
process tree (detected via the env var `ARTAGON_VSCODE_DEPRECATION_SEEN=1`
inherited by children) suppress. Setting `ARTAGON_VSCODE_DEPRECATION_ACK=1`
in the shell environment suppresses on every run with no end-of-run
summary; setting `ARTAGON_VSCODE_DEPRECATION_SUMMARY=1` enables an
end-of-run "X legacy invocations, deprecation window closes <date>"
line on stderr. Without any env var, default behavior is the
once-per-tree warning.

**Rationale**: original draft mandated per-invocation warnings; CI
workflows that loop over profiles flood stderr, ops teams response is
`2>/dev/null`, the deprecation deadline arrives unnoticed. Rate-limiting
preserves the signal-to-noise ratio while still surfacing the warning.

### Decision 21: Direct shell-script callers also get the deprecation shim

**Choice**: the deprecation alias for legacy profile names lives in
`scripts/lib/legacy-profile-name.sh` (sourced by `vspcli`,
`scripts/install-extensions.sh`, `scripts/compose-settings.sh`,
`scripts/export-profiles.sh`, and `scripts/import-profile.sh`). All five
entry points resolve `<flavor>-{crisp,retina}` → `<flavor>` + implied
`--ux=<look>` and emit the rate-limited deprecation warning per
Decision 20. README.md updates its CLI snippets to the new form during
the deprecation window so users learn the new shape before the legacy
form dies.

**Rationale**: README documents direct script invocations
(`bash scripts/install-extensions.sh web-astro-crisp`) — those callers
bypass `vspcli` and would hit a hard `Extensions file not found` error
post-migration. Pushing the alias into every script preserves the soft
landing.

### Decision 22: ARTAGON_RTK_WRAPPED is a process-local marker, not exported

**Choice**: in fish, `set -l ARTAGON_RTK_WRAPPED 1` (local, not exported)
inside a `function _rtk_install_wrappers ... end` invocation. In bash,
the marker is a regular shell variable (no `export`). Children of the
shell — including subshells, scripts spawned from tasks, `tmux` panes,
`ssh` sessions — do NOT inherit the marker, so they can install their
own wrappers if rtk is on PATH there.

**Rationale**: original draft used `set -gx` (global exported) which
meant every child inherited the marker, suppressing wrapping in places
the user actually wanted it (tmux panes, ssh sessions to rtk-aware
remote machines). The leak modes flagged in adversarial review go away
with a process-local marker.

**Trade-off**: a recursive call from rtk back into a wrapped command
would attempt to re-install the wrappers in a fresh subshell. The
function-based wrappers use `command rtk <cmd>` which short-circuits
to the real rtk binary directly, so the recursion never reaches the
wrapper definitions. The local marker is belt-and-suspenders: even if
recursion did reach the script, the local marker scopes the suppression
correctly.

### Decision 23: `docs/rust.md` is general-audience; CLI-emitted form is captured separately

**Choice**: `docs/rust.md` §11 stays in its current bare-`cargo doc` form
(general-audience, copy-paste-able by a Rust developer setting up VS
Code outside this repo's CLI). The CLI-emitted form (`rtk cargo doc`,
`rtk env RUSTDOCFLAGS=... cargo doc`) is captured in a new snapshot file
under the change at
`openspec/changes/workspace-toolchain-and-ux-layering/snapshots/rust-tasks.json`.
The BATS `rust-docs-settings.bats` test pins against this snapshot, NOT
against `docs/rust.md` directly. `docs/rust.md` §11 gains a footer note:
"For the CLI-emitted form (with rtk routing), see `vspcli --detect` in
a Rust workspace."

**Rationale**: adversarial review flagged the original draft as
self-contradictory ("pinned against the doc" but the doc has the bare
form). Decoupling lets the doc serve general Rust developers while the
CLI honors the workspace's rtk contract.

## Reference: rtk enforcement architecture

Concrete file shapes the CLI writes during `vspcli --detect` (and modifies
key-by-key on subsequent runs without trampling user-authored keys).

**`.vscode/settings.json`** (drop-in, key-by-key merged with existing).
The `<FISH_PATH>` and `<BASH_PATH>` placeholders below are replaced at
compose time with the resolved absolute paths from `command -v fish`
and `command -v bash` (Decision 13). The `--init-command` source path
uses `${workspaceFolder}` if VS Code substitutes it in
`terminal.integrated.profiles.*.args` (Open Question 1, validated
pre-merge); otherwise it's the absolute repo-clone path resolved at
compose time:

```jsonc
{
  // --- Terminal: route interactive shells through rtk-aware fish ---
  "terminal.integrated.profiles.osx": {
    "rtk-fish": {
      "path": "<FISH_PATH>",
      "args": [
        "--init-command",
        "source ${workspaceFolder}/_shared/rtk/rtk-init.fish"
      ],
      "icon": "terminal",
      "color": "terminal.ansiCyan",
      "overrideName": true
    },
    "rtk-bash": {
      "path": "<BASH_PATH>",
      "args": ["--rcfile", "${workspaceFolder}/_shared/rtk/rtk-init.bash", "-i"],
      "icon": "terminal",
      "overrideName": true
    }
  },
  "terminal.integrated.profiles.linux": {
    "rtk-fish": {
      "path": "<FISH_PATH_LINUX>",
      "args": [
        "--init-command",
        "source ${workspaceFolder}/_shared/rtk/rtk-init.fish"
      ]
    },
    "rtk-bash": {
      "path": "<BASH_PATH_LINUX>",
      "args": ["--rcfile", "${workspaceFolder}/_shared/rtk/rtk-init.bash", "-i"]
    }
  },
  "terminal.integrated.defaultProfile.osx": "rtk-fish",
  "terminal.integrated.defaultProfile.linux": "rtk-fish",
  "terminal.integrated.automationProfile.osx": {
    "path": "<FISH_PATH>",
    "args": [
      "--init-command",
      "source ${workspaceFolder}/_shared/rtk/rtk-init.fish"

  "terminal.integrated.env.osx": {
    "ARTAGON_RTK_REQUIRED": "1"
  }

```

When `command -v fish` returns nothing (fish not installed), the
`rtk-fish` entries are omitted from `profiles.*` and the
`defaultProfile.*` falls through to `rtk-bash`. When neither fish nor
bash is on PATH (very unusual), the entire terminal-profile block is
omitted with a stderr notice.

**`_shared/rtk/rtk-init.fish`** (sourced by the terminal profile;
re-source-safe, function-based wrappers, process-local re-wrap guard
per Decision 22):

```fish
# Source-only — do not exec. Idempotent: safe to source twice.

# Bail if rtk is missing — never silently mask commands.
if not type -q rtk
    echo "rtk not on PATH; aliases not installed" >&2
    exit 0
end

# Process-local marker — NOT exported. Children (tmux, ssh, scripts) do
# NOT inherit it, so they install their own wrappers if rtk is on PATH
# in their environment.
if set -q ARTAGON_RTK_WRAPPED
    exit 0
end
set -l ARTAGON_RTK_WRAPPED 1

function _rtk_wrap --argument-names cmd
    if type -q $cmd
        function $cmd --inherit-variable cmd --wraps=$cmd
            command rtk $cmd $argv
        end
    end
end

# Search & navigation per ~/.agents/SEARCH.md
_rtk_wrap rg
_rtk_wrap grep
_rtk_wrap find

# Build/test wrappers for the toolchains in this repo
for c in git npm pnpm yarn cargo rustc rustup mvn gradle make python python3 pip pip3 node deno bun
    _rtk_wrap $c
end

functions -e _rtk_wrap

# Workspace Trust diagnostic per Decision 14: emit success line so users
# in Restricted Mode (no rtk wrappers) notice the absence.
if status is-interactive
    echo "rtk wrappers active — workspace trust granted" >&2
end
```

**`_shared/rtk/rtk-init.bash`** (bash equivalent for users not on fish):

```bash
# Source-only. Idempotent. Process-local marker per Decision 22.
[ -n "${ARTAGON_RTK_WRAPPED:-}" ] && return 0
ARTAGON_RTK_WRAPPED=1  # NOT exported

if ! command -v rtk >/dev/null 2>&1; then
    echo "rtk not on PATH; aliases not installed" >&2
    return 0
fi

_rtk_wrap() {
    local cmd="$1"
    command -v "$cmd" >/dev/null 2>&1 || return 0
    eval "$cmd() { command rtk $cmd \"\$@\"; }"
}

for c in rg grep find git npm pnpm yarn cargo rustc rustup mvn gradle make python python3 pip pip3 node deno bun; do
    _rtk_wrap "$c"
done
unset -f _rtk_wrap

# Workspace Trust diagnostic per Decision 14
case $- in *i*) echo "rtk wrappers active — workspace trust granted" >&2 ;; esac
```

Both init scripts: (i) early-return if `rtk` is missing rather than
masking commands; (ii) use `ARTAGON_RTK_WRAPPED` env marker that prevents
re-wrapping when rtk itself shells out (children inherit env); (iii)
define functions, not aliases, so `command <cmd>` and `\<cmd>` escape
hatches still work; (iv) only wrap commands that actually exist on PATH.

## Reference: Workspace settings precedence (informs the JSONC merge contract)

Scope chain (low → high priority):

| # | Scope | Synced? | Notes |
|---|---|---|---|
| 1 | Default | n/a | Built-in core + extension defaults |
| 2 | User (`User/settings.json`) | yes | Per-machine global; only this layer is synced |
| 3 | Profile | yes (active profile only) | Active non-default profile shadows User |
| 4 | Remote | as remote | SSH/WSL/Container/Codespaces user-level on the remote |
| 5 | **Workspace** (`.vscode/settings.json`) | **no** | Repo-shared layer — what this CLI writes |
| 6 | Workspace Folder (per-folder `.vscode/settings.json`) | **no** | Multi-root only; beats Workspace for files inside |
| 7+ | Language-specific overrides at each scope | as parent | `"[rust]": { ... }` always beats non-language at same scope |

Merge semantics: **objects merge key-by-key across layers; primitives and
arrays replace wholesale.** No in-VS-Code mechanism to "delete" a key set in
a lower layer — only override.

Honored at workspace scope: settings declared as `machine-overridable`,
`window`, `resource`, or `language-overridable`. **Silently dropped at
workspace scope**: `application`-scoped, `machine`-scoped, and a hardcoded
executable-path safety blacklist (`git.path`, `terminal.external.*Exec`,
plus a few historical entries — full list in
`agents/skills/vscode-config/references/precedence.md`).

JSONC: comments and trailing commas are tolerated; **duplicate keys are
silent last-wins** — the CLI's JSONC merge dedupes before writing back.

Settings Sync: workspace settings are **NOT synced**. Only User scope is.

Workspace Trust: `terminal.integrated.profiles.*`,
`terminal.integrated.defaultProfile.*`,
`terminal.integrated.automationProfile.*`, custom shell tasks — all gated by
Workspace Trust. In Restricted Mode the rtk profile is silently dropped and
the terminal blocks open by default. **The change documents this as a
one-time trust-grant click on first open.**
